# Return clean errors when photo upload storage or the database connection fails

## Description
Serves US-3 (input household expenses). Photo uploads already work when everything is healthy (US-3-T-3). This task covers the failure paths added in PR #25: object storage that cannot sign a URL, one attachment that cannot be signed when a message is sent, and a database connection that dies mid-request. Out of scope: the happy-path upload flow (US-3-T-3), `GET /messages/:inviteCode` (it calls the same `publicAttachments` function), the app's `Composer` byte measurement, and the pool `keepAlive` setting.

## Specs
- `POST /conversations/:inviteCode/attachments` with a valid body (for example `{ "fileName": "receipt.png", "contentType": "image/png", "sizeBytes": 70 }`) when storage is configured but signing the upload URL throws:
  - returns HTTP 502 and `{ "error": "File storage is unavailable. Please try again later." }`;
  - inserts no row into `attachments`, so no `pending` row is left behind.
- `POST /messages/:inviteCode` with `attachmentIds` of confirmed uploads, where signing the download URL fails for one of them (a file name that `encodeURIComponent` rejects, such as a lone surrogate `"\ud800.pdf"`):
  - still returns HTTP 201 and the message is created;
  - `message.attachments` contains the attachments that could be signed, in the order sent, and omits the one that could not;
  - the failure is logged with `console.error`.
- `POST /messages/:inviteCode` when a query inside the transaction throws and the following `ROLLBACK` also throws (a dropped connection):
  - the error that reaches Express is the original query error, not the `ROLLBACK` error;
  - the `ROLLBACK` failure is logged with `console.error`;
  - the client is released with `release(true)` so the pool discards the broken connection, and it is released exactly once.
- A normal failure where `ROLLBACK` succeeds still releases the client without the discard flag.

## Requirements
- Tests use the existing fake pool and fake S3 server in `tests/upload_test_helpers.mjs`, or a small fake `pg` pool in the test file. No real database, bucket or network.
- No new runtime or dev dependencies; tests run with `node --experimental-strip-types --test`.
- Do not change `backend/` behavior. Existing tests (including `tests/attachment-*.test.mjs`) must keep passing.

## Acceptance criteria
1. When signing the upload URL fails, the upload request returns 502 with "File storage is unavailable. Please try again later.".
2. When signing the upload URL fails, no attachment row is created.
3. When one attachment cannot be signed, the message is still sent with HTTP 201.
4. The message response lists only the attachments that could be signed, in the order sent.
5. When `ROLLBACK` fails, the error passed to Express is the original error, not the `ROLLBACK` error.
6. When `ROLLBACK` fails, the connection is released once with `release(true)`.
7. When `ROLLBACK` succeeds, the connection is released once without the discard flag.
